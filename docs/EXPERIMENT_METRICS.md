# 项目全局静态分析增强实验：评价指标与统计方案

## 1. 实验问题

实验要回答的问题是：在项目、问题、大模型、系统指令、推理参数和工具预算均相同的前提下，增加项目全局静态分析产生的依赖图上下文与依赖查询能力，是否能提高大模型分析代码项目的质量。

当前实现中的处理变量为：

- 对照组（baseline）：中性 Manifest、中性 Repo Map，以及入口、符号、源码读取和全文搜索工具；不含图统计、图上下文和依赖邻居工具。
- 实验组（graph）：上述共同信息，加上依赖图摘要、有界节点/边上下文和 `get_dependency_neighbors` 工具。

因此，实验结论应表述为“当前全局静态依赖图增强方案的增量效果”，不能泛化成“所有静态分析必然有效”。

## 2. 评价原则

1. 采用同项目、同问题的配对实验，所有差值都按配对计算。
2. 先盲评、后揭盲；盲评前隐藏 Token、工具名、工具调用数等可能暴露组别的信息。
3. 答案质量是主要终点；耗时、Token 和工具调用只能作为成本或机制指标，不能替代质量指标。
4. 使用源码、测试、配置和静态分析产物共同建立标准答案，但不能直接把待验证的依赖图当作唯一真值。
5. 同时设置图敏感任务和图无关对照任务，避免把“回答更长”误判成“项目理解更好”。
6. 预先固定问题集、评分规则、主要指标、最小有意义差异和排除规则，再开始正式实验。

## 3. 问题集设计

### 3.1 图敏感任务

这些任务是检验全局静态分析价值的主体，建议占问题集的 60%。

| 类型 | 本项目可用问题形式 | 主要考查点 |
| --- | --- | --- |
| 跨文件调用链 | “一次项目导入如何从 API 进入 Loader、Analyzer、Manifest 和 Artifact Store？” | 有序节点、调用关系、跨文件路径 |
| 变更影响分析 | “修改 `UnifiedCodeAnalyzer.run_full_analysis` 可能影响哪些上游入口和下游产物？” | 入边、出边、可达模块、影响边界 |
| 架构与核心模块 | “项目的核心模块及其依赖方向是什么？” | 模块识别、中心节点、层次关系 |
| 入口到功能追踪 | “Agent 请求从 HTTP API 到模型调用和事件持久化的链路是什么？” | 入口、队列、Worker、编排器、Provider |
| 继承与重写 | “各语言 Handler 如何继承基类并参与分析流程？” | inherits、overrides、实际实现位置 |
| 循环与耦合 | “是否存在值得关注的模块级循环依赖或高耦合点？” | 环、边类型、证据和风险边界 |

### 3.2 一般项目理解任务

建议占问题集的 20%，例如入口、框架、模块职责、运行方式和数据产物。这类问题用于判断图增强是否也改善整体项目概览。

### 3.3 图无关负对照任务

建议占问题集的 20%，例如单个函数行为、某个配置项默认值、某个错误处理分支或 README 中明确给出的命令。图增强在这类任务上不应出现明显退化。若只测试调用链、影响分析等图敏感问题，只能证明图对特定题型有帮助，不能证明总体项目分析更好。

### 3.4 难度与覆盖

每个问题在实验前标注：

- 任务类型：图敏感、一般理解、图无关；
- 难度：简单、一般、困难；
- 涉及文件数和模块数；
- 标准答案中的必答事实、可选事实和禁止出现的错误事实；
- 是否存在静态分析无法可靠判断的动态行为。

若只有一个被测项目，结论仅适用于该项目。若希望证明方案具有普适性，应覆盖不同规模、语言、框架和依赖密度的多个项目，并始终在每个项目内部进行配对。

## 4. 主要质量指标

### 4.1 原子事实正确率（Factual Precision，FP）

将答案拆为可独立验证的事实陈述。每条事实标为正确 `1`、部分正确 `0.5`、错误 `0`；纯建议或无法验证的修辞不计入分母。

```text
FP = Σ事实得分 / 可验证事实数
```

路径、符号、入口、调用方向、数据流向和模块职责都应分别作为原子事实。FP 能防止包含大量正确内容但夹杂关键错误的长答案获得过高评价。

### 4.2 必答要点覆盖率（Required-point Recall，RR）

每道题预先建立标准要点表，并按重要性赋权：关键要点 `2`，次要要点 `1`。正确覆盖得满分，部分覆盖得一半，遗漏或错误得零分。

```text
RR = Σ(要点权重 × 覆盖得分) / Σ要点权重
```

该指标对应“完整性”，但比笼统的 1–5 星评分更容易复核。

### 4.3 依赖关系推理分（Relation Reasoning Score，RRS）

仅用于图敏感问题，按标准答案中的节点、关系和链路评分：

```text
RRS = 0.30 × 节点 F1 + 0.40 × 有方向/类型的边 F1 + 0.30 × 路径顺序得分
```

- 节点 F1：是否找到了问题涉及的正确文件、类、函数或模块；
- 边 F1：是否给出了正确方向和类型的 calls、imports、contains、inherits、overrides 等关系；
- 路径顺序得分：关键链路中相邻步骤和先后顺序的正确比例。

如果问题只要求影响集合而不要求完整路径，可将路径部分替换为受影响节点集合 F1。不要把 `contains` 当作 `calls`，也不要把“可能影响”写成“运行时必然调用”。

### 4.4 证据质量分（Evidence Quality Score，EQS）

当前系统输出 `[相对路径:行号]`，因此证据可以客观校验：

```text
引用有效率 CP = 有效且存在的引用数 / 全部引用数
证据蕴含率 CE = 确实支持相邻主张的引用数 / 全部引用数
关键主张覆盖 CC = 有有效引用的关键主张数 / 正确关键主张数
EQS = 0.30 × CP + 0.40 × CE + 0.30 × CC
```

“系统事件中收集了多少条 evidence”不能代替 EQS。自动附带的入口证据、重复证据或答案中没有实际引用的证据，都不应提高证据质量分。

### 4.5 幻觉率（Hallucination Rate，HR）

```text
HR = 无源码/配置/测试依据且被当成事实陈述的主张数 / 全部事实主张数
```

另记录严重幻觉率 `SHR`：虚构文件或符号、颠倒核心调用方向、虚构入口、声称执行过未执行的代码、把静态可能性断言为运行时事实，均视为严重幻觉。对于明确说“未确认”“可能”的合理不确定表达，不计为幻觉。

### 4.6 相关性与可用性（Relevance and Actionability，RA）

由盲评员按 1–5 分评分：

- 5：直接回答问题，结构清晰，结论与证据对应，可用于定位或决策；
- 4：核心答案清晰，只有少量冗余；
- 3：基本回答，但重点不够突出或缺乏可操作定位；
- 2：大量泛化描述，需读者自行整理；
- 1：偏题、不可用或未形成答案。

### 4.7 综合质量分（Grounded Analysis Score，GAS）

综合分用于排序和总体比较，所有分项仍须单独报告：

```text
GAS = 100 × (0.35 × FP + 0.25 × RR + 0.20 × EQS + 0.20 × RA_normalized)
```

其中 `RA_normalized = (RA - 1) / 4`。若出现严重幻觉，每条额外扣 5 分，单题最多扣 20 分，最终分数限制在 0–100。RRS 不并入总体分，而作为图敏感任务的关键专项指标单独报告，以避免只因题型不同改变总分含义。

## 5. 保留现有 1–5 分盲评时的锚点

当前界面已有正确性、完整性、证据充分和幻觉控制四项评分。正式实验中应向评审展示统一锚点：

| 分数 | 正确性 | 完整性 | 证据充分 | 幻觉控制 |
| --- | --- | --- | --- | --- |
| 5 | 无实质错误，关系和边界精确 | 全部关键要点和必要细节齐全 | 关键主张均有有效且能蕴含结论的引用 | 无幻觉，并正确表达不确定性 |
| 4 | 核心正确，仅有轻微瑕疵 | 仅遗漏次要要点 | 大部分关键主张有有效证据 | 无严重幻觉，至多一个轻微无依据主张 |
| 3 | 主结论基本正确，但有一处明显错误或含混 | 覆盖主要要点但遗漏明显 | 有证据但覆盖不全或部分证据弱 | 有少量不影响主结论的幻觉 |
| 2 | 存在影响结论的重要错误 | 只覆盖少数要点 | 多数结论无法由引用支持 | 有严重幻觉或多处无依据断言 |
| 1 | 主结论错误或无法回答 | 几乎未覆盖必答要点 | 无证据、引用无效或证据与结论无关 | 大量或核心幻觉 |

主观星级适合作为辅助指标和一致性检查，主要论文结论优先使用 FP、RR、RRS、EQS 和 HR 这些可审计指标。

## 6. 配对偏好指标

盲评员在不知道组别的情况下选择左侧更好、右侧更好或相当。揭盲后计算：

```text
图增强净胜率 = (图增强胜场 + 0.5 × 平局) / 有效配对数
```

同时报告胜/平/负原始数量和 95% 置信区间。偏好不能作为唯一主指标，因为答案长度、写作风格和展示顺序可能影响偏好。

## 7. 效率、稳定性与机制指标

### 7.1 效率指标

- 端到端执行耗时：从 Worker 实际开始到运行完成，不含排队等待；
- 首个答案或首个模型输出延迟；
- 供应商返回的实际输入、缓存输入、输出和推理 Token；
- 模型调用轮数、工具调用数、工具成功率和无效工具调用率；
- 图查询调用数，以及返回后被答案实际采用的比例；
- 每次答案成本，以及 `GAS / 每千 Token` 的质量效率。

字符数除以 4 的 Token 估算只能作临时观测值。它没有覆盖系统指令、问题、工具 schema、工具观察和后续模型轮次，不能用于正式成本结论。

### 7.2 稳定性指标

- 完成率：`completed / 所有计划运行`；
- 失败率、取消率和超步数后强制总结率；
- 同一问题多次重复运行的 GAS 标准差和四分位距；
- 最差 10% 问题的 GAS；
- 不同任务类型、难度、项目规模和语言下的效果差异。

“终态”不等于“成功”。failed 和 cancelled 配对应排除出答案质量评分，但必须进入可靠性统计，并按预注册规则重跑或记失败。

### 7.3 机制指标

机制指标用于解释为什么变好或变差，不用于直接判定答案好坏：

- 图上下文是否包含标准答案所需节点/边；
- 图工具是否被调用、参数是否有效、结果是否被引用；
- 首次定位正确文件所需的模型轮数；
- 读取源码文件数和搜索次数；
- 图本身的节点/边召回率与准确率。

如果图上下文本身没有覆盖标准答案所需关系，模型失败应区分为“静态分析/裁剪失败”和“模型使用失败”。

## 8. 实验执行与统计

### 8.1 重复与随机化

- 每道题至少独立重复 3 次，以降低模型采样波动；若模型支持固定 seed，应记录但仍建议多次重复；
- 左右展示顺序随机化；
- 两组启动顺序随机化或并发隔离执行；
- 固定模型版本、temperature、top_p、最大输出 Token、最大步骤数和超时；
- 保存项目提交哈希或不可变快照 ID、静态分析器版本和图产物哈希。

正式分析时先在“问题”层面对重复运行求均值，再做配对检验，或使用以问题为聚类单元的 bootstrap，避免把同一道题的多次采样当成完全独立样本。

### 8.2 评审一致性

- 每个答案对由至少 2 名评审独立盲评；分歧超过预设阈值时由第三人裁决；
- 1–5 分维度报告加权 Cohen's kappa 或组内相关系数；
- 原子事实和要点标签报告 Cohen's kappa；
- 评审员不能参与对应问题标准答案的临时修改。

### 8.3 统计报告

每个指标报告实验组与对照组的均值/中位数、配对差值、95% 置信区间和效应量：

- GAS、FP、RR、RRS、EQS、HR：配对 bootstrap 置信区间；必要时使用 Wilcoxon 符号秩检验；
- 胜/平/负：带平局处理的净胜率、bootstrap 区间或符号检验；
- 完成率和严重幻觉率：配对二元分析或 McNemar 检验；
- Token、耗时：优先报告中位数和 P90/P95，避免均值被长尾主导。

除总体结果外，必须按图敏感、一般理解和图无关三类分层报告。多项目实验应同时报告项目内效果和跨项目宏平均，不能让大项目的问题数量支配总体结果。

## 9. 建议的预注册判胜规则

以下阈值适合作为第一版，可在小规模 pilot 后、正式实验前调整一次：

1. 图敏感任务上，GAS 的平均配对提升至少 5 分，且其 95% 置信区间下界大于 0；
2. 图敏感任务上，RRS 的平均配对提升至少 0.08，且图增强净胜率高于 55%；
3. 图无关任务上，GAS 非劣效界限为 -3 分，即 95% 置信区间下界不低于 -3；
4. 严重幻觉率不得增加超过 2 个百分点；
5. 图增强组完成率不低于对照组，或差值不低于预设的 -2 个百分点；
6. 同时报告 Token、耗时和成本增幅。若质量达标但成本显著增加，应表述为质量—成本权衡，而不是无条件胜出。

只有同时满足质量提升、安全/可靠性不退化和可接受成本这三类条件，才建议判定全局静态分析增强方案整体胜出。

## 10. 当前实现需要先修正的测量风险

1. 盲评页面在揭盲前显示估算输入 Token、工具调用和证据数量。图增强组天然具有更长上下文并可调用图工具，评审可能据此猜出组别；这些数据应在提交盲评后显示。
2. 当前 `duration_ms` 使用运行记录的创建到更新时间，可能包含排队时间。两条运行又按 baseline 后 graph 的顺序创建，延迟比较会受到队列顺序污染；应记录 `started_at`、首个模型事件时间和 `finished_at`。
3. `execution_order` 虽被随机保存，但创建队列项仍固定先 baseline 后 graph；需要让实际认领/执行顺序与随机顺序一致，或使用隔离 Worker 并发执行。
4. 当前 Token 是字符估算，不是完整多轮模型用量；正式实验需记录供应商 usage。
5. 当前 `evidence_count` 是编排器收集并去重后的证据数，其中包含自动入口证据，不能说明答案中的引用有效或支持结论。
6. 当前比较状态把 completed、failed、cancelled 都作为终态，并允许进入盲评流程；质量分析必须区分成功完成与失败终止。
7. 即使模型名称相同，远端供应商也可能静默更新模型版本；应保存可获得的精确模型版本、参数、时间和请求标识。

## 11. 最小结果表

正式报告至少包含以下字段：

| 层级 | 必报内容 |
| --- | --- |
| 数据集 | 项目数、提交/快照、语言、规模、问题数、任务类型和难度分布 |
| 质量 | GAS、FP、RR、图敏感任务 RRS、EQS、HR、SHR |
| 偏好 | 图增强胜/平/负、净胜率、95% CI |
| 可靠性 | 完成率、失败率、重复运行方差、最差 10% 表现 |
| 效率 | 实际输入/输出 Token、成本、执行耗时中位数与 P95、工具调用成功率 |
| 统计 | 配对差值、95% CI、效应量、检验方法、评审一致性 |
| 分层 | 图敏感/一般/图无关，以及按项目、难度、语言和规模的结果 |

最终结论应优先回答三个问题：图增强在哪些任务上提高了多少质量、为此增加了多少成本、在哪些问题上无效或产生退化。
